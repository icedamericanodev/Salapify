# f4.67 Bills and spending, implementation report

Stamp: f4.67 (ships over the air, no version bump)
Branch: claude/salapify-accounts-tab-overhaul-vm3gm6
Source: the founder's uploaded "v4.65 production implementation specification",
built as the honest, offline, on-top-of-what-exists version. This is the first
module of the founder's chosen "Expenses and bills suite".

## Scope

A "Bills and spending" screen, reached from the Menu MONEY band, that reads
figures the person already entered into three plain lenses:

1. This month's spending split into "Committed" (bills set up as recurring,
   debt payments, card interest) vs "Everyday" (the rest), with a ratio bar.
2. Recurring bills projected across Weekly / Monthly / Yearly.
3. A due-date radar: what is due before the next payday, soonest first, with
   bank-adjusted dates and plain-English countdowns.

## Honesty first: what the spec asked for vs what shipped

The v4.65 spec was a large, mostly-fabricated blueprint. Declined to the founder
before any code (they chose "build the new ideas honestly"): a Riverpod rewrite
and feature-first restructure of a shipping app; a couple "Shared Vault" with
live partner sync and a real-time comment feed (impossible offline, Salapify has
no backend); a "Virtual Stash burner PAN generator" (generates card numbers, a
security and Play-policy red flag); an "AI mascot / AI Q&A" label (the exact
claim removed hours earlier in f4.66); hardcoded InstaPay/PESONet fees and a
mortgage formula (money facts needing verification and golden vectors); and
several modules already shipped honestly (Safe-to-Spend f4.62, Credit Radar
f4.63, Avalanche/Snowball f4.64, Statement PDF f4.66). The founder picked the
"Expenses and bills suite" to build honestly first.

"Fixed vs Variable" (the spec's words) became "Committed vs Everyday" because the
data can only honestly support "you committed to this" (a recurring bill, a debt
tag, accrued interest), never "this is a fixed/essential cost": a recurring
Netflix line is committed but not essential, and a manually-logged rent is
essential but not tagged. Labeling those Fixed/Variable would be wrong in both
directions.

## The money

No money engine changed. The new pure module `spending_breakdown.dart` composes
only what already ships:

- `spendingSplit` re-buckets exactly the expense universe `budgetSummary` counts
  (type == 'expense', this month), using the EXACT complement of the
  discretionary predicate the cash-flow pace already uses
  (`commitments.dart` `_discretionaryDailyPace`: `source == 'interest'`,
  `debtId`, or `recurringId`). Invariant, asserted in tests:
  committed + everyday == `budgetSummary`'s spent.
- `recurringBillsMonthly` sums existing recurring expense rows; `billsForPeriod`
  is a pure multiplier (weekly annualizes then divides by 52).
- The due-date radar renders the golden-locked `upcomingCommitments` unchanged.

It invents no number and stores no new data, so it can never disagree with the
Budget, Cash flow, or Debts screens.

## Reviews (both ran before finalizing; every must-fix implemented)

financial-coach (soundness and honesty): sound and honest, one must-fix.
1. The radar caveat claimed "minimums, not a full payoff", but `upcomingDues`
   falls back to a debt's FULL remaining balance when no minimum is saved (the
   hole `safeToSpendBuffer`'s `minsUnset` guard closes, which `upcomingCommitments`
   never got). Corrected to the truth: a no-minimum debt shows its full balance
   here, add a minimum to fix that.
2. Dropped "everyday spending you chose in the moment" (a manually-logged rent
   shows as everyday); reworded to "not tied to a bill or debt you set up", plus
   a "setting up a recurring bill moves it into committed" nudge.
3. Recolored Committed off the warning/alarm hue (it is mostly rent and debt,
   not a danger) to celebrate gold, accent left on Everyday (the actionable
   number).
4. "lands before payday" to "is due before payday" (a minimum does not leave the
   account without autopay).

qa-tester (crash and edge-case): one crash, closed.
1. A summation overflow (two near-max finite amounts sum to Infinity, then
   committedPct = Infinity / Infinity = NaN) would make the screen's `pct.round()`
   and the ratio-bar flex `round()` throw. Guarded `committedPct` in the engine
   and the flex in the screen to bail to 0 / a neutral bar, the same non-finite
   discipline `formatMoney` follows. Negative amounts cannot persist
   (`sanitizeData` floors expense amounts at 0, the guarantee `budgetSummary`
   relies on), and clamping would break the invariant, so left unclamped.

## What did NOT change

No money engine, schema, migration, or stored data. No new persisted setting
(the period toggle is ephemeral local state). No backend, no transmission. No
new bundled asset, so it ships over the air.

## Deferred (put to the founder)

1. Per-row flagging of a no-minimum debt in the radar (the caveat now explains it
   in prose; a per-row badge would need `upcomingCommitments` to expose which rows
   fell back to full balance).
2. The founder's module was named an "Expenses and bills suite"; this first cut is
   the bills-and-spending lens. A later cut could add category-level fixed/variable
   only if the data ever supports it honestly.
3. The parked f4.67-era "Chat with Pan" pill is still pending as a separate OTA.

## Risks

Low. Pure presentation over golden-locked engines, no data or money-methodology
change. The one honesty risk (the full-balance radar fallback) is now stated
truthfully on screen rather than contradicted.
