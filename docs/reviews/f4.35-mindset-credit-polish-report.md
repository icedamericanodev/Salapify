# f4.35 Credit polish: lock-in penalty + log-the-plan prompt, report

The bank officer's two optional polish items from f4.34, both founder-approved
and (for the score change) bank-officer verified before building.

## 1. Lock-in term penalty (money methodology)

A longer installment lock-in is more sustained exposure than a short one, but
before this a 12-month and a 3-month plan for the same price scored the same (the
income axis even rewarded the longer plan for its smaller monthly bite). The bank
officer pinned the curve:

    lockInPenalty(months) = clamp((months - 3) / 3, 0, 4)
    3mo -> 0 (baseline, the shortest term offered), 6mo -> 1, 12mo -> 3, cap 4

Applied to EVERY credit plan, not gated on a fee, because a 0% long plan still
locks you in. Folded with the existing markup penalty into one clamp so the score
is never clamped twice. Threaded through a new `termMonths` param on
mindsetDecision and a `months` field on creditScoreInputs; the flow passes
plan.months. Pure function of the term only (never scaled by the monthly bite,
which the income axis already reflects), so the two effects stay separable.

## 2. Log-the-plan prompt (UX nudge, no money change)

After buying on a plan, the result screen offers to log the monthly payment to
Recurring. commitmentLoad (the stacking guard) reads recurring bills and debt
minimums, so logging the installment makes the NEXT decision's income axis see
the commitment. The prompt writes nothing itself; it navigates to Recurring where
the user adds it (the app's "never auto-save, the person taps" convention).

## Money and data

Money-methodology change to the credit score only (lock-in). One-time and
subscription scoring untouched; the what-if spectrum is one-time-only and
unaffected. No storage or schema change.

- creditScoreInputs test carries the months field; a widget test confirms buying
